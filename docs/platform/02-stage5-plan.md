## 2. Схема базы

```
"user" ─┬─ account (хэш пароля)        companies ─┬─< company_members >─ "user"
        ├─ session                                ├─< invitations
        ├─ user_security (блокировка)              ├─< vacancies ─< applications >─ candidates
        └─ staff_roles (admin; manager позже)      │                  │                 ├─< files (резюме)
                                                   │                  ├─< stage_history  ├─< candidate_links (видео)
                                                   │                  ├─< presentations ─┼─ consents >─ consent_texts
                                                   │                  └─< client_feedback├─< internal_notes
                                                   └─< files (документы компании)        
audit_log, login_throttle, settings
```

Ключевые правила целостности в базе:
- `applications`: одна запись на пару «вакансия — кандидат»;
- `presentations`: не больше одного действующего представления на `application`; создание невозможно без действующего согласия цели «передача работодателю», подходящего этой компании (проверка триггером);
- отзыв согласия триггером закрывает все представления, созданные на его основании;
- `stage_history` и `audit_log` только пополняются: изменение и удаление строк запрещено правами роли приложения.

## 3. Права доступа

Проверяются в трёх местах:
1. **Сервер.** Каждый API-маршрут проверяет сессию, роль и принадлежность записи. Компания клиента берётся из сессии, а не из запроса.
2. **База.** Приложение работает под ролью без права обхода RLS. В каждой транзакции сервер передаёт только ID пользователя, а роль и компании база вычисляет сама по `staff_roles` и `company_members`. Поэтому отзыв доступа действует сразу и на уровне базы.
3. **Файлы.** Хранилище закрыто. Файл отдаёт только сервер после проверки прав на каждый запрос.

| Данные | Администратор | Клиент |
|---|---|---|
| Компании | все, создание и изменение | только своя, просмотр |
| Пользователи, приглашения, блокировка | все | нет |
| Вакансии | все, создание и изменение | только своей компании, просмотр |
| Пул кандидатов, контакты, заметки, согласия | всё | нет прямого доступа |
| Кандидат | все поля | только через своё действующее представление и только разрешённые поля |
| История этапов | вся | только по своему представлению, начиная с момента представления; внутренние этапы скрыты |
| Резюме: просмотр | да | если в представлении разрешён просмотр |
| Резюме: скачивание | да | если разрешено скачивание |
| Видео (ссылки) | да | если разрешено |
| Контакты кандидата | да | если разрешено |
| Решения «Интересен», «Интервью», «Отказ» | да, с отметкой «за клиента» | да (роль owner или member) |
| Обратная связь | да | да (owner или member) |
| Журнал действий | да | нет |

**Клиент не получает ID кандидата и ID файлов.** Карточка и резюме открываются по ID представления. Поэтому два клиента, которым показали одного кандидата, не могут сопоставить данные. Если запись чужая или доступ отозван, ответ всегда 404.

## 4. Вход, приглашения, сессии

**Приглашение.**
1. Администратор указывает почту, компанию и роль в компании.
2. Сервер создаёт случайный токен (32 байта). В базе хранится только его SHA-256. Срок действия 72 часа, использовать можно один раз. Новое приглашение на ту же почту отменяет предыдущее.
3. Письмо со ссылкой `/invite/<токен>`.
4. Человек открывает ссылку, вводит имя и пароль (не короче 10 символов). Переход по ссылке из письма подтверждает почту.
5. Сервер создаёт пользователя и учётную запись через внутренний механизм Better Auth (пароль хэшируется scrypt), добавляет членство в компании, помечает приглашение использованным и открывает сессию.
6. Первый администратор создаётся командой `npm run create-admin -- email@...`: команда выводит ссылку приглашения в консоль сервера. Паролей в коде и репозитории нет.

**Вход.** Собственный маршрут `/api/session/login` вызывает вход Better Auth и добавляет ограничение попыток:
- по почте: после 5 неверных попыток за 15 минут вход блокируется на 15 минут, даже с верным паролем;
- по IP: не больше 30 попыток за 15 минут;
- для несуществующей почты поведение и ответ такие же, чтобы нельзя было проверить, есть ли аккаунт;
- заблокированный пользователь получает тот же общий ответ.

Прямой маршрут входа Better Auth снаружи закрыт: наружу открыты только выход, получение сессии, запрос и выполнение сброса пароля.

**Сессии.** Сессия хранится в базе, в браузере только cookie `HttpOnly`, `SameSite=Lax`, в рабочем режиме `Secure`. Срок без активности — 30 минут, общий срок — 12 часов (настраиваются). Кэш сессии в cookie выключен: каждая проверка идёт в базу, поэтому отзыв действует со следующего запроса. Изменяющие запросы принимаются только с собственного домена (проверка Origin).

**Восстановление пароля.** Маршрут Better Auth `request-password-reset` всегда отвечает одинаково. Письмо уходит, только если пользователь существует и не заблокирован. Токен на 1 час, в базе хранится в виде хэша. После смены пароля все сессии пользователя закрываются.

**Отзыв доступа.**
- Блокировка пользователя: отметка в `user_security` и удаление всех его сессий. Вход невозможен.
- Отзыв членства в компании: доступ к данным компании пропадает со следующего запроса, на уровне и сервера, и базы.
- Отзыв представления или согласия: кандидат и его файлы перестают открываться у клиента сразу. Сами данные кандидата при этом не удаляются: удаление и сроки хранения — по юридическим правилам, которые предстоит согласовать.

## 5. Что используется из Better Auth

Проверено по коду установленной версии 1.7.7.

| Используем | Как |
|---|---|
| `emailAndPassword` | вход, хэширование scrypt, `disableSignUp: true` (открытая регистрация отклоняется), длина пароля 10–128 |
| Сброс пароля | `requestPasswordReset`, `resetPassword`, `sendResetPassword` (наша отправка письма), `revokeSessionsOnPasswordReset: true`, токен на 1 час |
| Хранение токенов | `verification.storeIdentifier: "hashed"`: токены сброса хранятся в виде хэша |
| Сессии | таблица `session`, `getSession`, `signOut`, `deleteUserSessions`; `cookieCache` выключен |
| Ограничение частоты | встроенный ограничитель для открытых маршрутов Better Auth, хранение в базе |
| Внутренний адаптер | `createUser`, `createAccount`, `password.hash` — для создания приглашённых пользователей |

**Не используем:** регистрацию, вход через соцсети, подтверждение почты отдельным письмом (его заменяет ссылка приглашения), плагины `admin` и `organization` (роли и компании храним в своих таблицах).

**Двухфакторный вход для администраторов** (плагин `twoFactor`) не входит в этот этап, чтобы не расширять объём. Предлагаю включить до запуска с реальными данными.

**Ограничение Better Auth.** Токен сессии хранится в таблице `session` в открытом виде, cookie при этом подписана. Утечка базы позволила бы перехватить действующие сессии. Риск снижают короткие сроки сессий и шифрование базы на стороне провайдера.

## 6. Отправка писем

Модуль `mailer` с тремя режимами:
- `file` — письма сохраняются в папку проекта; для локальной разработки, ссылку можно открыть оттуда;
- `memory` — для автотестов;
- `smtp` — для рабочего запуска через почтовый сервис по SMTP.

Кандидаты для рабочего режима — Yandex Cloud Postbox или Unisender Go. Сервис не выбран и не подключён. Перед подключением нужно проверить условия, тарифы и размещение данных, затем настроить SPF и DKIM на домене. Получатели писем — пользователи кабинета, их почта тоже персональные данные.

Шаблоны: приглашение (текст из документа о контенте), сброс пароля. В письмах только ссылка и общий текст, без данных кандидатов.

## 7. Локальная проверка

Да, этап делается и проверяется полностью локально:
- **PostgreSQL 16** запускается из локальных программ без Docker (`scripts/dev-db.sh`), автотесты поднимают отдельную временную базу;
- **файлы** в автотестах хранятся в закрытой папке вне публичного каталога (драйвер `local`). Драйвер `s3` для Yandex Object Storage проверяется на локальном эмуляторе S3 (moto), без облака;
- **письма** пишутся в файл или в память;
- **данные** только вымышленные; вместо резюме — сгенерированные тестовые PDF.

На вашем компьютере тот же набор можно запустить через `docker-compose.yml` (PostgreSQL, MinIO, Mailpit). Docker в моей среде не запущен, поэтому этот файл я проверить не могу и отмечу его как непроверенный.
