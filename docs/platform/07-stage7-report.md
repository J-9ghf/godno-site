## 1. Сессии и cookie: проверка конфигурации (вариант А)

Механизм Better Auth 1.7.7 не менялся. Проверено в исходном коде библиотеки и тестами `session-config.test.ts`. Для тестов поднимается сервер в рабочем режиме с HTTPS-адресом.

| Что | Как сейчас | Проверка |
|---|---|---|
| Secure | Если адрес сайта начинается с `https://`, все cookie получают `Secure` и префикс `__Secure-`: браузер не отправит их по HTTP и не даст подменить с поддомена. В рабочем режиме сервер не запускается с адресом без HTTPS | Тест |
| HttpOnly | У всех cookie: скрипты страницы токен не видят | Тест |
| SameSite | `Lax`: cookie не уходит с запросами POST с других сайтов | Тест |
| Domain | Не задаётся: cookie действует только на адресе кабинета, без поддоменов | Тест |
| Срок | Cookie сессии живёт 30 минут и продлевается при активности. Абсолютный предел — 12 часов, после него сессия удаляется. Промежуточная cookie 2FA между паролем и кодом живёт 10 минут | Тесты этапов 5 и 7 |
| Отзыв | Каждая проверка идёт в базу, кэша сессий нет. Блокировка, смена и сброс пароля, сброс 2FA, отзыв членства и «выйти везде» действуют сразу | Тесты этапов 5 и 6 |
| CSRF | Три уровня. Сервер отклоняет изменяющие запросы к API без своего Origin, включая `null` и похожие адреса. Better Auth проверяет доверенные адреса. Astro отдельно отклоняет отправку форм с чужого адреса. Выход и другие действия выполняются только методом POST | Тест: запросы без Origin, с чужим Origin, с `null` и в виде text/plain-формы отклоняются, данные не меняются, сессия не закрывается |
| Встраивание страниц | `X-Frame-Options: DENY`, CSP `frame-ancestors 'none'`, HSTS при HTTPS | Тест |
| Ошибки настроек | Сервер с неверными настройками (нет ключа, слабый ключ, адрес без HTTPS в рабочем режиме) останавливается при первом обращении и не обслуживает запросы | Тест |

### Ключ сервера: что он защищает и что будет при утечке

Ключ используется для двух вещей:
1. **Подпись cookie сессии.** Токен сессии в базе без ключа бесполезен.
2. **Шифрование секретов 2FA и резервных кодов в базе.**

| Что утекло | Последствия |
|---|---|
| Только база или её копия | Войти по токенам нельзя (тест этапа 6). Секреты 2FA зашифрованы. Остаются риски самой утечки данных: имена, контакты, хэши паролей (scrypt) |
| Только ключ | Сам по себе входа не даёт: нужен токен действующей сессии, а он есть только в базе и в браузере пользователя |
| База и ключ вместе | Злоумышленник может подделать cookie любой действующей сессии (тест это подтверждает) и расшифровать секреты 2FA. Это главный довод хранить ключ отдельно от базы и копий |

**Действия при подозрении на утечку ключа:**
1. Выпустить новый ключ и удалить старый из `BETTER_AUTH_SECRETS`. Все сессии закроются сразу (тест).
2. Сбросить 2FA всем администраторам. Секреты, зашифрованные старым ключом, после его удаления не расшифровываются, а в случае утечки их нужно считать раскрытыми. Затем администраторы настраивают 2FA заново (тест). Сброс выполняется командой `npm run reset-2fa -- почта` или в кабинете вторым администратором.
3. Выпустить новые пароли базы и хранилища, если они могли утечь вместе с ключом.
4. Проверить журнал действий за период, оценить инцидент и при необходимости уведомить Роскомнадзор (см. блокирующие задачи).

### Ротация ключа

**Найденный риск.** Раньше ключ был один (`BETTER_AUTH_SECRET`). Его плановая замена молча сломала бы 2FA у всех администраторов: секреты 2FA перестали бы расшифровываться.

**Устранено настройкой, без смены механизма.** Подключена встроенная в Better Auth 1.7.7 поддержка ключей с версиями — `BETTER_AUTH_SECRETS`:
- первый ключ подписывает cookie и шифрует новые данные;
- остальные только расшифровывают ранее зашифрованное.

Порядок для рабочего сервера:

| Шаг | Значение | Что происходит |
|---|---|---|
| Запуск | `BETTER_AUTH_SECRETS=1:<ключ>` | Все данные шифруются с версией ключа |
| Плановая ротация (например, раз в год) | `2:<новый>,1:<старый>` | Все пользователи выходят и входят заново. 2FA продолжает работать: старые данные расшифровываются ключом 1, новые шифруются ключом 2 |
| Удаление старого ключа | `2:<новый>` | Только после того, как все администраторы заново настроили 2FA. Иначе у них 2FA перестанет работать до сброса |

Все три шага проверены тестом, в том числе переход с ключа без версии (`BETTER_AUTH_SECRET`) на ключи с версиями.

**Где хранить:**
- Yandex Lockbox. Доступ только у сервисного аккаунта приложения и у ответственного администратора.
- Не в базе, не в резервных копиях, не в Git, не в переписке.
- В Git ключ не попадает: `.env` исключён, а тест `repo-hygiene.test.ts` проверяет все файлы репозитория на ключи, пароли и токены. Тест проверяет и сам себя: находит заложенные образцы.

### Остаточные риски и предложения (механизм не менялся)

| Риск | Оценка | Варианты |
|---|---|---|
| Токены сессий в базе без хэширования | Низкий при раздельном хранении ключа и базы | Вариант А принят. Вариант Б (хэширование) остаётся запасным |
| Код из приложения 2FA можно использовать повторно в течение 30–60 секунд: Better Auth не запоминает использованные коды | Низкий: нужен и пароль, и подсмотренный в эти секунды код | Можно запоминать использованные коды на нашей стороне. Около половины дня работы, механизм сессий не затрагивает. Сделаю по вашему решению |
| Подмена `X-Real-IP` при неверной настройке прокси обходит ограничение попыток по IP | Устраняется настройкой | `TRUST_PROXY=true` только за своим прокси, который перезаписывает заголовок. Пункт есть в контрольном списке |

## 2. Антивирусная проверка: настоящий ClamAV

Проверка типа файла не считается антивирусной проверкой и не заменяет её.

**Проверено с настоящим ClamAV 1.5.4** (`clamd` локально, `clamav-real.test.ts`):
- чистый PDF принимается со статусом «проверен»;
- PDF с тестовым вирусом (EICAR) и PDF с тестовым маркером отклоняются, не сохраняются в хранилище, попытка попадает в журнал с названием сигнатуры;
- ClamAV недоступен — загрузка отклоняется;
- файл больше лимита ClamAV не считается чистым;
- повторная проверка находит заражённый файл, загруженный при выключенной проверке, и отправляет его в карантин. Файл не открывается ни клиенту, ни администратору, выбрать его для клиента нельзя.

**Ограничение.** Официальные базы сигнатур скачать не удалось: сетевая политика среды разработки не пускает к `database.clamav.net`. Поэтому `clamd` работал со своей тестовой базой: EICAR и маркер. Это проверка связки и поведения при сбоях, но не охвата реальных угроз. На рабочем сервере с официальными базами проверку нужно повторить по `clamav.md`.

**Добавлено:**
- журнал отклонённых заражённых файлов;
- карантин для администратора;
- команда `npm run rescan-files` — повторная проверка файлов, например после обновления баз;
- инструкция `docs/platform/clamav.md`.

## 3. Репозиторий и история

**Закрыть репозиторий сам я не могу.** У меня нет доступа к настройкам видимости репозитория на GitHub. Порядок действий:

1. Откройте https://github.com/J-9ghf/godno-site → **Settings** (нужны права владельца).
2. Внизу страницы **General** — раздел **Danger Zone** → **Change repository visibility** → **Change visibility** → **Make private**.
3. Подтвердите: введите `J-9ghf/godno-site` и пароль или код 2FA GitHub.
4. Проверьте в окне без входа в GitHub, что https://github.com/J-9ghf/godno-site отвечает 404.
5. Если сайт развёртывается из репозитория (например, Vercel), откройте настройки проекта на хостинге. Убедитесь, что у приложения GitHub есть доступ к закрытому репозиторию, и выполните пробное развёртывание.
6. Желательно: включить 2FA на аккаунте GitHub и проверить список имеющих доступ (Settings → Collaborators).

Структура проекта и история при этом не меняются. Публичных форков нет (на момент проверки — 0).
