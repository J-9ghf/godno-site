12 октября 2026. Всё сделано локально: без облачных ресурсов, платных подключений и реальных персональных данных. Все данные в тестах вымышленные, почта — на домене `example.test`.

## 1. Двухфакторная аутентификация администратора

Использую плагин `twoFactor` из Better Auth 1.7.7, который уже стоит в проекте. Новых библиотек и внешних сервисов нет, кроме `qrcode`: она рисует QR-код в браузере.

- **Включение** (раздел «Безопасность и согласия»). Администратор вводит пароль, сканирует QR-код в приложении-аутентификаторе (Яндекс Ключ, Google Authenticator и другие) и подтверждает включение кодом. Одновременно выдаются 10 одноразовых резервных кодов.
- **Хранение.** Секрет и резервные коды хранятся в базе в зашифрованном виде; ключ — секрет сервера.
- **Принуждение.** При `ADMIN_2FA_REQUIRED=true`, а это значение по умолчанию, администратор без 2FA получает доступ только к её настройке. Остальные разделы закрыты и в интерфейсе, и в API: сервер отвечает 403 `two_factor_required`.
- **Вход.** Сначала пароль, затем код из приложения или резервный код. До ввода кода сессии нет.
  - Код действует 10 минут после ввода пароля.
  - После серии неверных кодов вход блокируется.
  - Функция «доверенное устройство» отключена на сервере: поле `trustDevice` удаляется из запроса.
- **Восстановление доступа:**
  1. Резервный код (каждый работает один раз). Новые коды можно выпустить по паролю, старые при этом перестают действовать.
  2. Сброс другим администратором в разделе «Пользователи и доступы». Сбросить собственную 2FA нельзя. Все сессии пользователя закрываются, при следующем входе 2FA настраивается заново.
  3. Аварийный сброс из консоли сервера: `npm run reset-2fa -- email`. Нужен, если администратор один.
  - Все действия попадают в журнал.
  - Сброс пароля по почте 2FA **не отключает**.
  - Самостоятельно отключить 2FA нельзя.
- **Проверено:**
  - 12 тестов API (`twofactor.test.ts`);
  - 2 браузерных теста: вход с кодом через страницу входа и кабинет администратора без 2FA.

## 2. Сессии: хранение токенов в базе

**Как в Better Auth 1.7.7.**
- Токен сессии хранится в таблице `session` в открытом виде. Встроенного хэширования токенов в этой версии нет.
- Cookie `ikr.session_token` содержит токен и подпись HMAC-SHA256, сделанную секретом `BETTER_AUTH_SECRET`. Сервер принимает cookie только с верной подписью. Режим входа по заголовку Bearer не подключён.

**Что это значит.**
- Если утечёт только база или её резервная копия, без секрета сервера, войти по токену нельзя: подделать подпись невозможно. Это проверено тестом: «токен из базы без подписи сервера не работает».
- Если утекут и база, и секрет, злоумышленник сможет войти под чужими действующими сессиями до их истечения.
  - Срок жизни сессии без активности — 30 минут, максимум — 12 часов.
  - У администраторов 2FA не защищает уже открытую сессию.

**Варианты:**

| Вариант | Суть | Последствия |
|---|---|---|
| А. Оставить механизм, усилить окружение (**рекомендую сейчас**) | Секрет хранится в Lockbox отдельно от базы и копий. Копии шифруются, сроки сессий короткие. Блокировка, смена пароля и сброс 2FA закрывают сессии сразу | Изменений в коде нет, библиотека обновляется без риска |
| Б. Хэшировать токен в базе | Обёртка над адаптером базы Better Auth: при записи и поиске сессии токен заменяется на SHA-256 | Зависит от внутреннего устройства Better Auth: после каждого обновления нужен регрессионный тест. В списке сессий будут хэши вместо токенов. При переходе все действующие сессии закрываются. Работы — около дня вместе с тестами |
| В. Сменить механизм сессий | Своя реализация или другая библиотека | Переписывать вход, приглашения, восстановление пароля и 2FA. Не рекомендую |

Механизм я не менял. Если выберете вариант Б, сделаю его отдельной задачей до запуска.

**Добавлено:**
- смена пароля в профиле: требует текущий пароль, закрывает остальные сессии;
- «Выйти на всех устройствах»;
- администратор может завершить все сессии пользователя;
- в списке пользователей видно число активных сессий и включена ли 2FA.

**Тесты сессий:**
- `sessions.test.ts`, 5 тестов: подпись cookie, смена пароля, выход на всех устройствах, завершение администратором, истёкшая сессия не продлевается;
- из этапа 5, `auth.test.ts`: блокировка закрывает сессию сразу, истечение по бездействию и по 12 часам, закрытие сессий после сброса пароля;
- из этапа 5, `isolation.test.ts`: отзыв членства закрывает доступ сразу.

## 3. Файлы

| Требование | Как сделано |
|---|---|
| Тип файла | Тип определяется по содержимому (сигнатуре), а не по расширению и заголовку браузера. Резюме — только PDF |
| Размер | Лимит по виду файла, но не больше `MAX_UPLOAD_MB` (15 МБ). У PDF — не больше 60 страниц |
| Проверка содержимого | PDF разбирается pdf.js на сервере. Повреждённые и зашифрованные файлы отклоняются |
| Вредоносные PDF | Отклоняются файлы со скриптами (на уровне документа, страниц, полей форм и аннотаций), запуском программ (Launch), вложенными файлами, мультимедиа, формами XFA, отправкой форм и импортом данных, ссылками на внешние файлы. Проверяются и маркеры в самом файле, и объекты, которые находит pdf.js, в том числе в сжатых потоках |
| Антивирус | Готов клиент ClamAV по протоколу INSTREAM. Если ClamAV недоступен, файл отклоняется, а не считается чистым. Пока ClamAV не развёрнут, работает `FILE_SCAN_MODE=off`, и в карточке файла написано «антивирусная проверка выключена». При `FILE_SCAN_MODE=clamav` клиенту можно открыть только файл со статусом «проверен» |
| Хранение | Закрытое хранилище: локальная папка вне публичного каталога или закрытый бакет S3. Ключи файлов случайные |
| Доступ к каждому файлу | Файл отдаёт только сервер после проверки прав при каждом запросе. Прямых и временных ссылок на хранилище нет. Ответ отдаётся с заголовками `no-store`, `nosniff` и CSP `sandbox`. Клиент обращается к файлу по ID представления, ID файла ему не известен |
| Загрузка не открывает доступ | В представлении нужно явно выбрать конкретный файл резюме (`resume_file_id`); это проверяет и база. Новая загрузка не меняет то, что видит клиент. Файл другого кандидата выбрать нельзя |
| Просмотр и скачивание | Отдельные права. Просмотр — в карточке через pdf.js на canvas, без встроенного просмотрщика браузера. Пометка с компанией, почтой и датой — не защита, а метка |

Тесты: `file-security.test.ts` — явный выбор файла, 7 видов опасных PDF, обычный PDF принимается, ClamAV (чистый, заражённый, недоступен). Плюс тесты файлов из этапа 5.

## 4. Кабинеты

Страница `/app` открывается только после входа. Разметка, стили и логика взяты из демоверсии. Данные приходят из API, права проверяют сервер и база при каждом запросе.

**Клиент.**
- Дашборд: показатели, воронка, причины отказов, «Ждут вашего решения».
- «Мои кандидаты»: доска и список с фильтрами, сравнение 2–4 кандидатов.
- Карточка кандидата: разбор, комментарий рекрутера, видео-ссылки и контакты по правам, резюме (просмотр и скачивание по правам), история этапов, отзывы, решения «Интересен», «Интервью», «Отказ» с причиной. Наблюдатель только просматривает.
- «Вакансии» с воронкой по каждой.
- «Профиль»: смена пароля, выход на всех устройствах.

**Администратор.**
- Дашборд с фильтрами (компания, вакансия, период) и таблицей по клиентам.
- Клиенты и карточка клиента: вкладки «Обзор», «Пользователи», «Вакансии», «История».
- Вакансии и кандидаты по вакансии: этапы, представление клиенту с выбором файла и прав, отзыв представления, история.
- Пул и карточка кандидата: данные, файлы, ссылки, согласия, заметки, рассмотрения.
- Пользователи и доступы: блокировка, сессии, сброс 2FA, приглашения, роли, матрица прав.
- Журнал действий.
- Безопасность и согласия: 2FA, пароль, версии текстов согласий.

**Чатов нет:** ни раздела, ни API. Это проверяется в браузерных тестах.

**Изменения при переносе:**
- Просмотр PDF использует legacy-сборку pdf.js. Основная сборка 6-й версии требует функций JavaScript, которых нет в распространённых браузерах; в тестовом Chromium она не работала.
- В строке файла кнопки перенесены, чтобы имя файла не обрезалось.

**Не перенесено** (как в плане): входящие заявки, интервью, документы и счета, каталог услуг, настройка названий этапов. Эти разделы остаются в демоверсии.

## 5. Показатели

Одна функция в базе считает всё по истории этапов.
- Когорта — дата первого представления.
- «Обработано» — дата добавления к вакансии.
- Клиент видит только действующие представления своей компании; администратор видит также отозванные.
- Для администратора добавлена сводка по компаниям, для клиента — воронка по каждой вакансии.

Тесты (`metrics-isolation.test.ts`, 6 тестов, плюс `metrics.test.ts` из этапа 5):
- решения компании B не попадают в конверсии и отказы компании A;
- цифры клиента совпадают с цифрами администратора по той же компании;
- работают фильтры по компании, вакансии и периоду;
- клиент не получает сводку по компаниям и чужие вакансии.

**Опубликованная демоверсия (артефакт):**
- Текущая версия без пароля: вход по паролю отключён, данные вымышленные.
- Доступ — «по ссылке» (ваша настройка).
- В ранних версиях артефакта был демонстрационный пароль `demo-ikr-2026`.
- Демоверсия загружает шрифты с Google Fonts. Для страницы без реальных данных это допустимо; рабочая платформа хранит шрифты у себя.

**Рекомендую (настройки я не менял):**
1. Сделать репозиторий закрытым до запуска: Settings → General → Danger Zone → Change visibility. Если публичным должен остаться только сайт, вынести платформу в отдельный закрытый репозиторий.
2. Не хранить в репозитории внутренние документы (`.docx`, договоры, выгрузки). Если документы из истории считаются конфиденциальными, можно переписать историю (`git filter-repo`), но это ломает чужие копии, и уже скачанное не вернуть. Проще закрыть репозиторий.
3. Демоверсию держать с доступом «по ссылке», не размещать в ней реальные данные и не связывать с рабочими адресами. Старые версии артефакта с паролем, если они видны в истории версий, можно удалить: в них только вымышленные данные.
4. Секреты рабочей системы — только в Lockbox и переменных окружения. Для локальной разработки — `.env`, который уже в `.gitignore`.
5. Включить в GitHub Secret scanning и Push protection (бесплатно для публичных репозиториев, для закрытых нужен Advanced Security) или запускать gitleaks перед пушем.
