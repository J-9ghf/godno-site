# Этап 5. Отчёт: ядро платформы

12 октября 2026. Всё сделано и проверено локально, без облачных ресурсов, платных сервисов и реальных персональных данных.

## Что готово

**База данных** (`platform/db/`):
- две роли: `ikr_owner` (миграции) и `ikr_app` (приложение, без обхода RLS);
- 4 миграции: таблицы входа Better Auth, ядро (компании, пользователи и роли, приглашения, вакансии, кандидаты, рассмотрения, история этапов, представления, обратная связь, заметки, файлы, ссылки, согласия и версии текстов, журнал, настройки), права доступа (RLS и функции), представления для клиента и функция показателей;
- целостность в базе: история этапов пишется триггером при каждой смене этапа, история и журнал только пополняются, представление невозможно без действующего подходящего согласия, отзыв согласия триггером закрывает представления.

**Вход и доступ** (`platform/src/lib/`, `src/pages/`):
- Better Auth: вход по почте и паролю, регистрация отключена, сессии в базе без кэша в cookie, сброс пароля с хэшированным токеном на 1 час;
- приглашения: токен 32 байта, в базе только SHA-256, 72 часа, одноразовые, повторное приглашение отменяет прежнее;
- первый администратор: `npm run create-admin -- почта`, пароль задаёт сам человек;
- ограничение попыток: 5 за 15 минут по почте и 30 по IP, блокировка на 15 минут, одинаковое поведение для существующей и несуществующей почты;
- блокировка пользователя и отзыв членства действуют со следующего запроса;
- сессия: 30 минут без активности, не более 12 часов всего;
- проверка Origin у изменяющих запросов, заголовки безопасности, Content-Security-Policy на страницах;
- страницы: вход, приглашение, восстановление пароля, новый пароль, временная страница кабинета. Дизайн взят из демоверсии, шрифт Manrope подключён локально (без Google Fonts).

**API ядра:**
- администратор: компании, приглашения, пользователи (блокировка, отзыв доступа), вакансии, кандидаты, ссылки на видео и Яндекс Диск, заметки рекрутера, тексты согласий и согласия (фиксация, отзыв), рассмотрения и этапы, представления с отдельными правами (просмотр резюме, скачивание, видео, контакты), отзыв представления, показатели с фильтрами (компания, вакансия, период), журнал;
- клиент: обзор компании и вакансий, список и карточка представленных кандидатов, решение («Интересен», «Интервью», «Отказ» с обязательной причиной), отзыв, резюме (просмотр и скачивание по отдельным правам), показатели.

**Файлы:**
- драйверы хранилища: локальная закрытая папка и S3 (для Yandex Object Storage);
- тип определяется по содержимому; PDF проверяется pdf.js, повреждённые и защищённые паролем файлы отклоняются;
- лимиты: 15 МБ для документов, 5 МБ для фото;
- ключи объектов случайные, без исходного имени файла;
- выдача только через сервер с проверкой прав на каждый запрос, без кэширования, в изолированном контексте; просмотры и скачивания записываются в журнал.

**Прочее:**
- демо-пароль удалён из `prototypes/ikr-platform.html`. Опубликованная демоверсия обновлена по той же ссылке: вход по паролю там отключён, кнопки демо-доступа работают;
- `scripts/backup.sh` и `scripts/restore-check.sh`, инструкция `backup-restore.md`;
- корневой `tsconfig.json` исключает `platform`, сборка сайта ИКР проходит.

## Отличия от плана

- **Без Drizzle ORM.** Запросы написаны на SQL через `pg`, миграции — SQL-файлы. Так проще проверять права и RLS, и меньше зависимостей. На архитектуру не влияет.
- **Запись ролей при принятии приглашения** выполняет узкая функция базы `grant_invitation`. Она работает только для действующего приглашения и только для пользователя с той же почтой. Прямой записи ролей в обход RLS нет.
- **Клиенту не передаются ID кандидатов и файлов.** Всё открывается по ID представления, чтобы два клиента не могли сопоставить данные одного кандидата.
- **TypeScript 6** закреплён в `platform`, как и у сайта: `astro check` не поддерживает TypeScript 7. При этом `astro check` в связке Astro 7 и TypeScript 6 даёт ложные ошибки в собственных типах Astro, поэтому код проверяется через `tsc`. Вернусь к этому при обновлении инструментов.

## Ограничения и что не сделано

- **Экраны кабинетов** (дашборды, доска кандидатов, карточка, админка) не перенесены. Это этап 6. Сейчас после входа открывается временная страница, данные доступны через API.
- **Просмотр PDF внутри карточки** (pdf.js в браузере, водяной знак) — этап 7. Серверная часть с раздельными правами готова и проверена.
- **Двухфакторный вход для администраторов** не включён. Предлагаю включить до работы с реальными данными.
- **Антивирусная проверка файлов** (ClamAV) не подключена. Поле статуса проверки в базе есть.
- **Письма** реально не отправляются: сохраняются в папку. Режим SMTP написан, но не проверен с настоящим сервисом.
- **`docker-compose.yml`** не проверен: Docker в моей среде не запущен.
- **Токен сессии** Better Auth хранится в базе открыто (cookie подписана). Риск снижают короткие сроки сессии и шифрование базы у провайдера.
- **Не перенесено:** интервью, документы компании (договоры и счета), услуги, публичные формы сайта, запрос замены — вторая очередь по плану.
- **Чаты** пока остаются в демоверсии. Их удаление — этап 8, в новом коде их нет.
- **Старые версии опубликованной демоверсии.** В их истории остался демо-пароль. Он ничего не открывает: у демоверсии нет сервера и реальных данных.

Соответствие 152-ФЗ этим этапом **не подтверждается**: для этого нужны проверка инфраструктуры, договоров и юридических документов.
