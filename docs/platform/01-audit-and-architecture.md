## Этап 1. Что есть сейчас

### 1.1. Стек и файлы

В репозитории `godno-site` два независимых продукта.

| Что | Где | Стек | Как работает |
|---|---|---|---|
| Основной сайт ИКР | `src/`, `public/` | Astro 7 (статическая сборка), TypeScript, без UI-фреймворков | Статические страницы. Форма заявки только проверяет поля, данные никуда не отправляет (`src/scripts/main.ts`) |
| Демоверсия платформы | `prototypes/ikr-platform.html` | Один HTML-файл: CSS, разметка, чистый JavaScript (~2 650 строк, 300 КБ) | Лендинг, вход и три кабинета. Нет сервера, нет сборки, нет зависимостей кроме шрифта Manrope |

Серверного кода, базы данных, переменных окружения, CI и тестов в репозитории нет. В `astro.config.mjs` указан `site: 'https://example.com'`, адаптера для серверного режима нет.

### 1.2. Как устроена демоверсия

Код в файле разделён на слои, это сильно упростит переход:

1. **Данные** — функция `seed()` создаёт демо-набор. Хранилище `LocalAdapter` пишет всё в `localStorage` браузера.
2. **Слой доступа `api.*`** — 60 функций. Экраны меняют данные только через них. Внутри есть проверки прав (`need`, `companyScope`, `assertCompany`, `stageRule`).
3. **Показатели `views.*`** — воронка, конверсии, сроки, причины отказов, гарантия. Чистые функции над строками.
4. **Интерфейс** — функции `cDash`, `cCands`, `tDash`, `tPipeline` и др. собирают HTML-строки. Обработчики событий в объектах `A` (клики), `C` (изменения), `F` (формы).

Главный вывод: данные берутся **только из демо-массивов в браузере**. Каждый посетитель видит свою копию, ничего не сохраняется на сервере, права проверяются в коде, который пользователь может изменить в своём браузере. Это нормально для прототипа и недопустимо для MVP.

### 1.3. Экраны

**Кабинет клиента:** Дашборд · Мои кандидаты (доска, список, карточка, сравнение 2–4) · Заявки (новая заявка, гарантия, запрос замены) · Интервью · Документы · Услуги · **Сообщения** · Профиль и коллеги.

**Кабинет менеджера:** Дашборд · Мои клиенты · Входящие · Кандидаты и этапы · Пул кандидатов · Интервью · Документы · **Сообщения** · Запросы услуг.

**Кабинет администратора:** Дашборд · Клиенты и карточка клиента · Заявки · Пул кандидатов · Кандидаты по заявкам · Интервью · Документы и счета · Каталог услуг · **Сообщения** · Пользователи и доступы · Журнал действий · Настройки.

**Публичное:** лендинг из 16 блоков, форма заявки работодателя, форма резюме, страница входа.

### 1.4. Что работает только как демонстрация

| Функция | Что сейчас | Что нужно |
|---|---|---|
| Хранение всех данных | `localStorage` браузера | PostgreSQL на сервере |
| Вход | Кнопки демо-доступа и **пароль `demo-ikr-2026`, записанный в коде страницы** | Серверная авторизация, хэши паролей, сессии. Пароль из кода удалить |
| Сессия | `localStorage`, без срока действия | Cookie `HttpOnly`, `Secure`, серверная сессия с истечением |
| Блокировка после 5 попыток | Счётчик в памяти страницы, сбрасывается перезагрузкой | Ограничение на сервере по аккаунту и IP |
| Приглашения | Запись в массив, письмо не отправляется | Письмо с одноразовой ссылкой, токен хранится в виде хэша |
| Восстановление пароля | Только текст на экране | Письмо со ссылкой, ограниченной по времени |
| Резюме с сайта | Сохраняются только имя и размер файла | Загрузка в защищённое хранилище с проверкой файла |
| Карточка кандидата: видео | Нарисованный плеер | Ссылка на видео или файл, выдача после проверки прав |
| «Скачать» документы и резюме | Всплывающее сообщение | Выдача файла через сервер с проверкой прав |
| Права доступа | Проверки в браузере | Проверки на сервере и правила доступа в базе |
| Превью кабинета на лендинге | Читает данные клиента в обход проверки прав | Статичная картинка или обезличенный пример |
| Сброс демо-данных | Кнопка на экране входа | Убрать |
| Telegram-бот | Только метка источника у заявок | В объём MVP не входит (см. вопросы) |
| Подпись документов клиентом | Смена статуса | Оставить как «ознакомлен», юридическую подпись не имитировать |

### 1.5. Чаты, которые нужно удалить (этап 8)

Всё найдено в одном файле, на другие функции чаты не завязаны:

- данные: массив `messages` в `seed()`, таблица `messages`;
- слой данных: `api.getThreads`, `api.getMessages`, `api.sendMessage`, тип события `message` в ленте и журнале;
- экраны: раздел `tMessages`, пункт «Сообщения» в меню всех ролей, вкладка «Сообщения» в карточке клиента;
- кнопки: «Переписка по заявке» (заявки клиента), «Переписка» (блок заявки у команды), «Сообщения» (карточка кандидата), «Новая тема по кандидату»;
- обработчики `openThread`, `newThread`, формы `msgForm`, `threadForm`;
- стили `.msgs`, `.threads`, `.thread`, `.conv-*`, `.bub`;
- строка «Сообщения» в матрице ролей.

Остаются: комментарий рекрутера для клиента, обратная связь по интервью и кандидатам, причины отказа, история этапов, журнал действий.

### 1.6. Что можно взять в MVP без изменений

- весь дизайн: CSS, токены, сетка, компоненты, адаптив;
- разметку экранов (функции, которые собирают HTML);
- модель данных: таблицы и названия полей уже близки к целевым;
- правила переходов между этапами (`stageRule`);
- формулы показателей (`views.*`), их нужно перенести в SQL;
- валидацию форм (телефон, Telegram, тип и размер файла).

Переделать придётся: слой `api.*` (вместо работы с массивами — запросы к серверу), загрузку данных экранами (сейчас синхронно, станет асинхронно) и весь сервер.

## Этап 2. Архитектура

### 2.1. Требования, которые определяют выбор

1. **Локализация.** Персональные данные граждан РФ при сборе должны записываться в базу, расположенную в России (ч. 5 ст. 18 152-ФЗ). Это касается и формы на сайте, и резюме, и почты пользователей кабинета.
2. **Защищённость.** Провайдер должен иметь подтверждённое соответствие требованиям 152-ФЗ, чтобы не строить защиту инфраструктуры самостоятельно.
3. **Маленькая команда.** Нужны управляемые сервисы: резервные копии, обновления и отказоустойчивость берёт на себя провайдер.
4. **Файлы.** Резюме PDF, фото, документы и, возможно, видео. Нужно хранилище с закрытым доступом и временными ссылками.
5. **Текущий стек.** Сайт сделан на Astro и TypeScript, демоверсия — на чистом JavaScript.

### 2.2. База данных

| Вариант | Плюсы | Минусы | Вывод |
|---|---|---|---|
| **PostgreSQL как управляемый сервис в российском облаке** (Yandex Cloud, Selectel) | Связи и транзакции, правила доступа на уровне строк (RLS), представления для показателей, автоматические копии и восстановление на момент времени, данные в РФ | Платно с первого дня; настройка сети и доступа | **Рекомендую** |
| PostgreSQL на своей виртуальной машине | Дешевле | Копии, обновления, мониторинг и защиту делаем сами | Только если бюджет критичен |
| Supabase, развёрнутый на своём сервере в РФ | Готовые вход, хранилище файлов, RLS, интерфейс | Около десятка сервисов, от 4–8 ГБ памяти, обновления и поддержка на нас | Слишком тяжело для команды без DevOps |
| Supabase Cloud, Firebase, Airtable, Google Таблицы | Быстрый старт | Серверы за рубежом: нарушение требования о локализации | **Исключены** для персональных данных |
| MongoDB, YDB и другие нереляционные | Масштабирование | Модель «кандидат — вакансия — клиент — этап» реляционная, права и метрики сложнее | Не подходит |
| SQLite (PocketBase и т. п.) | Очень просто | Один сервер, слабые копии и права | Не для персональных данных |

### 2.3. Хранение файлов

| Вариант | Вывод |
|---|---|
| **S3-совместимое хранилище того же российского провайдера** (Yandex Object Storage, Selectel S3) | **Рекомендую.** Закрытый бакет, шифрование на стороне хранилища, временные подписанные ссылки, версии объектов, дёшево за гигабайт |
| Файлы в самой базе (bytea) | База быстро растёт, копии тяжелеют. Не нужно |
| Диск сервера приложения | Пропадёт при пересоздании сервера, нет отдельных копий. Не нужно |
| Яндекс Диск по публичным ссылкам | Только как внешний источник видео, который добавляет рекрутер. Ссылка «у кого есть ссылка» — это фактически открытый доступ, вопрос вынесен юристу |

**Видео:** в MVP — только ссылки (Яндекс Диск, Rutube и т. п.). Загрузку видео-файлов в хранилище можно включить позже: технически это тот же механизм, но объёмы и трафик дороже.

### 2.4. Авторизация

| Вариант | Плюсы | Минусы | Вывод |
|---|---|---|---|
| **Better Auth** — библиотека на TypeScript, данные в нашей PostgreSQL | Вход по почте и паролю, отключение открытой регистрации, хэширование scrypt, встроенное ограничение частоты запросов, сессии в базе, восстановление пароля, двухфакторная проверка, блокировка пользователей. Всё в нашей базе в РФ | Приглашения в связке с нашими компаниями придётся собрать самим; версии библиотеки меняются, настройки по умолчанию нужно проверять | **Рекомендую** |
| Keycloak на своём сервере | Зрелая система, роли, 2FA | Отдельный тяжёлый Java-сервис, сложная настройка и обновления | Избыточно для MVP |
| Вход Supabase (GoTrue) | Хорош в связке с Supabase | Тянет за собой весь Supabase | Не берём, раз не берём Supabase |
| Auth0, Clerk, Firebase Auth | Удобно | Серверы и данные пользователей за рубежом | Исключены |
| Писать с нуля | Полный контроль | Высокий риск ошибок в безопасности | Не нужно |

Lucia, которую часто советуют, больше не развивается как библиотека, поэтому её не рассматриваю.

### 2.5. Приложение

Не переписываем на React или другой фреймворк. Делаем отдельное приложение `platform/` в этом же репозитории:

- **Astro в серверном режиме** (адаптер Node) — тот же стек, что у сайта;
- страницы кабинета используют **существующие CSS и функции отрисовки** из демоверсии, вынесенные в модули TypeScript;
- **серверные API-маршруты** `/api/...` заменяют функции `api.*`: каждая проверяет сессию и права, затем выполняет запрос к базе;
- запросы к базе через **Drizzle ORM** (типизация, миграции в SQL-файлах, есть адаптер для Better Auth);
- показатели — **SQL-представления** с теми же формулами, что сейчас в `views.*`.

Основной сайт остаётся статическим. Его формы заявки и резюме будут отправлять данные в API платформы, а не хранить их у себя.

### 2.6. Рекомендуемая схема

```
Браузер ─HTTPS─► Caddy (TLS) ─► Приложение Astro (Node, Docker) ─┬─► Managed PostgreSQL (РФ)
                                    │ проверка сессии и прав          ├─► Object Storage, закрытый бакет (РФ)
                                    │                                 ├─► Почта: Yandex Cloud Postbox или Unisender Go (РФ)
                                    │                                 └─► SmartCaptcha для публичных форм
                                    └─ ClamAV: проверка загружаемых файлов (по желанию)
```

**Провайдер: Yandex Cloud** (альтернатива — Selectel). Всё в одном провайдере: база, файлы, сервер, почта, капча, ключи шифрования (KMS), хранилище секретов (Lockbox), мониторинг. По официальной странице Managed PostgreSQL инфраструктура защищена в соответствии со 152-ФЗ, ISO 27001/27017/27018 и ГОСТ Р 57580.1. Уровень защищённости, который покрывает провайдер, нужно подтвердить документами при заключении договора.

**Почему не Selectel по умолчанию.** По открытым источникам я не смог подтвердить, что управляемый PostgreSQL Selectel входит в его аттестованный сегмент: там прямо упомянуты облачные и выделенные серверы и S3. Если для вас важнее цена или у вас уже есть договор с Selectel, архитектура переносится без изменений кода: везде используются PostgreSQL и S3-совместимое хранилище.

Разработку можно начать **без каких-либо внешних сервисов**: локально в Docker поднимаются PostgreSQL, MinIO (S3-совместимое хранилище) и Mailpit (перехват писем). Там же пройдут все автотесты. Облако понадобится только для развёртывания.

Когда будете готовы развернуть:

1. Вы регистрируете платёжный аккаунт Yandex Cloud на юрлицо или ИП (нужны реквизиты и договор; сделать это за вас я не могу и не должен).
2. Создаёте облако и каталог, назначаете мне сервисный аккаунт с правами только на этот каталог.
3. Ключи передаются через переменные окружения среды или Lockbox, **не через чат и не в репозиторий**.
4. Даёте доступ к DNS домена для поддомена кабинета и записей почты (SPF, DKIM).
5. Я создаю ресурсы только после того, как вы подтвердите их список и стоимость.

## Этап 3. Структура данных и права

### 3.1. Главная идея модели

Кандидат хранится **один раз** в пуле. Его рассмотрение по каждой вакансии — отдельная запись `applications`. Показ клиенту — ещё одна отдельная запись `presentations` с перечнем того, что именно открыто этому клиенту. Поэтому:

- один кандидат может идти по нескольким вакансиям разных клиентов;
- клиент А видит кандидата, только если есть активное представление по **его** вакансии;
- клиент Б не узнает, что кандидата показывали клиенту А: история этапов привязана к `applications`, а не к кандидату;
- доступ к резюме, видео и контактам открывается по каждому представлению отдельно.

### 3.2. Таблицы

Названия этапов те же, что в демоверсии, плюс два внутренних этапа, которые клиент не видит.

**Компании и пользователи**

| Таблица | Основные поля | Примечание |
|---|---|---|
| `companies` | id, name, sphere, city, contact_name, phone, email, status (active/paused/archived), created_at | Клиенты агентства |
| `users` | id, email (уникальный), name, email_verified, is_blocked, blocked_at, blocked_reason, created_at | Таблица Better Auth, пароля здесь нет |
| `accounts` | user_id, provider ('credential'), password_hash | Хэш пароля (scrypt), создаётся Better Auth |
| `sessions` | id, user_id, token_hash, expires_at, ip, user_agent | Серверные сессии |
| `staff_roles` | user_id, role (admin / recruiter) | Внутренняя команда. Таблица пустая — значит не сотрудник |
| `staff_assignments` | user_id, company_id | Если понадобится роль рекрутера с назначенными клиентами |
| `company_members` | company_id, user_id, role (owner / member / viewer), permissions (jsonb), revoked_at | Пользователи клиента. Задел на несколько пользователей с разными правами |
| `invitations` | id, email, company_id, member_role, token_hash, expires_at (72 ч), invited_by, accepted_at, revoked_at | Токен хранится только в виде хэша |

**Подбор**

|---|---|---|

| `inbound_requests` | id, source (site/telegram), contact_name, contact, company_name, position_type, tried, budget, status, assigned_to, converted_company_id, consent_id, created_at | Заявки с сайта до появления компании |

### 3.5. Кто что видит

Права проверяются в трёх местах: **сервер** (каждый API-маршрут), **база** (политики RLS как второй рубеж), **хранилище** (файлы выдаются только сервером после проверки).

| Действие | Администратор | Рекрутер (по желанию) | Клиент: owner | Клиент: member | Клиент: viewer |
|---|---|---|---|---|---|
| Компании: создать, изменить | да | нет | свою: только просмотр | просмотр | просмотр |
| Пользователи и доступ | все | нет | коллег своей компании (позже) | нет | нет |
| Вакансии | все | назначенных клиентов | свои | свои | свои |
| Пул кандидатов | весь | весь | нет | нет | нет |
| Кандидат | все поля | все поля | только через активное представление, только открытые поля | то же | то же |
| Контакты кандидата | да | да | если `share_contacts` | если `share_contacts` | нет |
| Резюме PDF | да | да | если `share_resume` | если `share_resume` | если `share_resume` |
| Скачивание PDF | да | да | если `allow_resume_download` | если разрешено | нет |
| Внутренние заметки | да | да | **никогда** | никогда | никогда |
| Решение «Интересен», «Интервью», «Отказ» | да, с отметкой | нет | да | да | нет |
| Обратная связь | да | да | да | да | нет |
| Согласия, обращения субъектов, журнал | да | просмотр | нет | нет | нет |

**Правило показа клиенту.** Представление нельзя создать, если у кандидата нет действующего согласия с целью «передача работодателю», подходящего для этого клиента. Проверка выполняется на сервере и повторяется ограничением в базе. При отзыве согласия все представления по нему автоматически закрываются, клиент перестаёт видеть кандидата и его файлы.

**Защита от подмены ID.** Клиентские запросы не принимают `company_id` от браузера: компания берётся из сессии. Любой запрос по ID кандидата, вакансии или файла сначала проверяет принадлежность компании пользователя. При отказе ответ всегда «не найдено» (404), чтобы нельзя было узнать, что запись существует.

### 3.6. Показатели

Всё считается в SQL-представлениях из `applications`, `presentations`, `stage_history`, `interviews`. Ручных цифр нет.

| Показатель | Точное правило |
|---|---|
| Активные вакансии | `vacancies.status` не в (closed, cancelled, paused) |
| Обработано кандидатов | Уникальные `candidate_id` в `applications` по вакансиям клиента за период, на любом этапе, включая внутренние. Клиент видит только число |
| Представлено | Количество `presentations` (кандидат × вакансия); отдельно — уникальные кандидаты |
| На рассмотрении у клиента | Активные представления, у которых текущий этап `offered` |
| Назначенные интервью | `interviews` со статусом «назначено» или «перенесено» и датой в будущем; отдельно — проведённые за период |
| Офферы, наймы | Представления, у которых в `stage_history` есть `offer` или `hired` (или более поздний этап) |
| Конверсия между этапами | Когорта представлений за период (по дате представления): доля дошедших до следующего этапа, по истории этапов |
| Время до первого кандидата | Первое представление по вакансии минус дата открытия вакансии |
| Срок закрытия | Дата `hired` минус дата открытия вакансии |
| Причины отказов | Группировка отказов по причине |

**Фильтры администратора:** компания, вакансия, период. Для воронки период применяется к дате представления (когорта), для событийных показателей (интервью, наймы) — к дате события. Обе логики будут подписаны на дашборде, чтобы цифры не путали.

Дашборд всегда запрашивает свежие данные при открытии и при каждом изменении этапа, без кэша показателей. Предрасчёт понадобится, только если данных станет очень много.

### 3.7. Резюме PDF: рекомендация

**MVP: вариант A плюс существующая структурированная карточка.**

- Карточка кандидата остаётся как в демоверсии: опыт, ожидания, разбор рекрутера (кто это, что движет, риски, горизонт, мнение), этапы, интервью. Эти поля заполняет рекрутер, это его работа, а не данные из PDF.
- Добавляется вкладка «Резюме»: оригинальный PDF открывается внутри карточки во встроенном просмотрщике (pdf.js) с водяным знаком «для [компания], [дата]». Кнопка «Скачать» есть, только если в представлении разрешено скачивание.
- Файл отдаётся сервером потоком после проверки прав, без постоянной ссылки. Каждый просмотр и скачивание записывается в журнал.

**Следующий шаг: вариант B как помощник рекрутера, а не автоматика.**

- При загрузке сервер извлекает текст из PDF и предлагает черновик полей: опыт, образование, навыки.
- Рекрутер проверяет, исправляет и подтверждает. Клиент видит только подтверждённые поля, оригинал остаётся доступен.
- Если в документе чего-то нет, поле остаётся пустым. Сканы без текстового слоя распознаются, только если подключить OCR; иначе поля заполняются вручную.
- Языковые модели для разбора резюме по умолчанию не используются: отправка резюме во внешний сервис — это передача персональных данных третьему лицу. Если захотите, можно рассмотреть российскую модель после согласования с юристом.

**Проверка загрузок:** только PDF, DOC, DOCX, JPG, PNG; проверка по сигнатуре файла, а не только по расширению; размер до 15 МБ для документов и 5 МБ для фото; отказ от зашифрованных и повреждённых PDF; новое имя объекта в хранилище (оригинальное имя хранится отдельно); при включённом ClamAV — антивирусная проверка до того, как файл станет доступен.

## Вопросы для юриста по персональным данным

Перед запуском с реальными кандидатами:

1. **Роли сторон.** ИКР — оператор персональных данных кандидатов. Кто клиент-работодатель при получении резюме: третье лицо, которому данные передаются, или самостоятельный оператор? Нужен ли с клиентами отдельный договор о конфиденциальности и целях использования?
2. **Форма и содержание согласия.** Достаточно ли галочки на сайте? Нужно ли отдельное согласие на каждую цель (хранение в базе, передача работодателю, видео и фото)? Общее согласие на передачу «работодателям» или отдельное по каждому работодателю? Какие актуальные требования к оформлению согласия (отдельный документ, перечень данных, срок)?
3. **Как доказывать согласие.** Какие сведения хранить: версию текста, дату, IP, способ получения? Нужна ли подпись для согласий, полученных не через сайт?
4. **Уведомление Роскомнадзора.** Подано ли уведомление об обработке персональных данных, нужно ли внести изменения: новые цели, место хранения, состав данных?
5. **Локализация и трансграничная передача.** Текущий сайт и тестовые адреса размещены на Vercel (за рубежом): можно ли через него собирать данные хотя бы временно? Telegram-бот, почта и мессенджеры менеджеров: есть ли трансграничная передача и нужно ли уведомление? Как быть, если клиент находится за рубежом (например, семья в Дубае)?
6. **Уровень защищённости.** Какой уровень защищённости информационной системы нужен, требуется ли модель угроз, какие организационные документы (политика, приказы, ответственный)?
7. **Провайдер облака.** Нужен ли договор поручения обработки с провайдером, какие документы о соответствии запросить?
8. **Сроки хранения и уничтожение.** Сколько хранить резюме в базе, после отказа, после найма? Как оформлять уничтожение (акты, журнал)? Как обезличивать данные для статистики?
9. **Отзыв согласия.** В какой срок прекратить обработку? Что делать с материалами, которые уже переданы клиенту?
10. **Видео и фото кандидатов.** Не относятся ли они к биометрическим данным в нашем сценарии? Допустимо ли хранить видео по ссылкам Яндекс Диска с доступом «по ссылке»?
11. **Специальные категории.** Сведения о здоровье, судимости, привычках (часто спрашивают у нянь и водителей): можно ли их собирать и на каком основании?
12. **Отзывы клиентов о кандидатах.** Это тоже персональные данные кандидата: нужно ли предоставлять их кандидату по запросу?
13. **Пользователи кабинета.** Основание обработки данных сотрудников клиента (почта, ФИО, журнал входов) и срок хранения журналов.
14. **Инциденты.** Процедура и сроки уведомления Роскомнадзора об утечке, ответственный, шаблоны.
15. **Политика обработки.** Нужно обновить политику и согласие: сейчас в них упоминаются Tilda, старые адреса и ссылка на заглушку.
